# AI 应用开发面试题（生产实战版）

重点考察"系统设计 + 生产踩坑"，不是背模型参数。每个答案都按
"生产中怎么做 → 为什么 → 常见追问"组织。

## 一、API 工程化（第一周）

### 1. 调用大模型 API，生产上要做哪些错误处理？

**生产答案：**

- **可重试错误**：429 限流、5xx、网络超时 → 指数退避重试（1s/2s/4s），设最大次数
- **不可重试错误**：400 参数错、401 鉴权错、内容安全拒绝 → 直接走告警，重试只会浪费钱
- **超时**：区分连接超时和读超时；流式场景用读超时断流检测
- **降级**：主模型不可用自动切备用模型（关键业务）；或返回兜底话术 + 告警
- **熔断**：连续失败熔断一段时间，防止雪崩

**坑**：不带节流直接重试，会把限流打得更死；重试要带 jitter（随机抖动）。

### 2. 结构化输出（JSON mode）生产上怎么保证可靠？

**生产答案：**

分四层防御：

1. **请求层**：response_format 指定 JSON mode（或 JSON Schema），prompt 里给明确 schema 和示例
2. **校验层**：模型返回的 JSON **必须**再过 Pydantic 校验，不合法直接拦截
3. **重试层**：校验失败把错误信息拼进 prompt 自动重试 1-2 次（"你上次输出的 price 应为 number"）
4. **兜底层**：仍失败则降级人工或规则处理，记录日志进评估集

**坑**：只信 JSON mode 不校验 = 事故预定；模型偶尔会输出 ` ```json ` 包裹或注释。

### 3. 流式输出（SSE）怎么实现？出问题怎么处理？

**生产答案：**

- 服务端：FastAPI `StreamingResponse` + `AsyncGenerator`，逐 chunk `yield`
- 协议：SSE，`data: {...}\n\n` 格式；工具调用场景 chunk 里会有增量参数，要拼装
- **断流处理**：读超时检测，断了给用户明确提示，已生成的部分不丢
- **异常兜底**：流中间出异常，先推一个错误事件再关流，前端才知道出了事
- 记录完整响应到日志（异步落库，不阻塞流）

### 4. Prompt 应该怎么管理？散落在代码里行不行？

**生产答案：**

不行。生产做法：

- 提示词与代码分离：放配置文件/数据库，带版本号
- **每次改动跑评估集回归**，不然改好一个 case 坏三个 case
- 变量用占位符模板，用户输入必须走 `human` 角色/明确分隔，不能拼进 system
- 记录每次请求的 prompt 版本，出问题可复现

### 5. token 怎么计算？上下文超限怎么处理？

**生产答案：**

- 用官方 tokenizer（tiktoken）估 token；中文 1 字 ≈ 1-2 token
- 长对话管理：按 token 预算裁剪历史（保留最近 N 轮 + 首轮重要信息），或定期摘要压缩
- RAG 场景：检索内容不是越多越好，超过预算优先丢弃低分块
- **写入日志**：每次请求的 prompt/completion token、耗时，成本才能核算

## 二、RAG 系统（第二周）

### 6. 设计一个生产级 RAG 系统，讲讲完整链路。

**生产答案（离线 + 在线两条链路，这是满分结构）：**

**离线（建索引）：**
1. 文档解析（PDF/Word/HTML）→ 清洗（去页眉页脚、乱码检测）
2. 分块（结构优先 + 大小控制）
3. 向量化 + 关键词索引，连同元数据（标题、来源、权限、时间）入库
4. 幂等：文档更新时按 doc_id 覆盖旧分块

**在线（查询）：**
1. query 预处理：改写、补全、敏感词过滤
2. 混合检索：向量 + BM25，结果融合
3. 重排：rerank 模型精排 TopK
4. 组装 prompt：system 约束 + 检索内容（带来源标记）+ 用户问题
5. 生成 + 引用标注（回答必须能溯源）
6. 落日志：命中文档、检索得分、token、用户反馈

**每个环节都可能成为瓶颈，所以需要评估集来定位。**

### 7. 分块策略怎么选？chunk 大小怎么定？

**生产答案：**

| 策略 | 适用 | 缺点 |
|------|------|------|
| 固定长度 | 简单、快速上手 | 语义被切断 |
| 递归分隔（\n\n → \n → 句号） | 通用默认 | 无结构感知 |
| 按标题/章节 | 结构化文档、知识库 | 依赖解析质量 |
| 语义分块（embedding 相似度断点） | 质量要求高 | 慢、成本高 |

- 经验起点：中文 300-500 token，overlap 10-20%
- **太大**：检索不准、噪声进 prompt、token 浪费；**太小**：上下文碎片化，答案缺前因后果
- 最终靠评估集调：固定问题集，试不同 chunk_size，看 recall@k

### 8. Embedding 模型怎么选？相似度用什么算？

**生产答案：**

- 选型维度：中文效果（MTEB 中文榜）、维度（存储成本）、推理速度、部署方式
- 常见：OpenAI text-embedding-3、BGE（开源中文强）、自部署 bge-m3
- 相似度：余弦相似度为主（向量归一化后点积等价）
- **坑**：换 embedding 模型必须全量重建索引，维度和语义空间都变了；入库和查询必须用同一个模型

### 9. 向量数据库怎么选型？

**生产答案：**

- **Chroma/Qdrant**：中小规模、快速起步（Qdrat 生产单机/集群都行）
- **Milvus**：大规模、有运维团队
- **pgvector**：数据本来在 PostgreSQL、规模中等，不想多加组件
- **ES/OpenSearch**：混合检索友好（BM25 + 向量一起查）
- 选型真正要回答：数据量级、QPS、是否需要元数据过滤、运维成本、团队熟悉度

### 10. 检索不准（RAG 效果差）怎么优化？

**生产答案（先定位再优化，顺序别乱）：**

1. **先搭评估集**：30-100 个真实问题 + 标准答案 + 相关文档，不然优化是玄学
2. **定位问题层**：检索层（该召回的没召回）还是生成层（召回了答不对）
3. 检索层优化：混合检索（BM25+向量+RRF）、query 改写/扩展、重排、元数据过滤、调 chunk 策略
4. 生成层优化：prompt 约束、引用标注、temperature 调低、few-shot
5. 每改一处，跑评估集回归，用数据说话

### 11. RAG 系统怎么评估质量？

**生产答案（离线 + 线上两套指标）：**

- **检索指标**：recall@k（标准文档是否在 TopK 里）、MRR（排名位置）
- **生成指标**：忠实度（答案是否被资料支撑）、答案相关性（是否答到点上）、引用准确性
- **工具**：RAGAS / 自建评估集 + LLM-as-judge（judge 模型要固定，避免自己评自己）
- **线上指标**：点踩率、人工抽检、回答采纳率
- **核心观点**：没有评估集的 RAG 项目无法迭代，先建评估集再谈优化

## 三、Agent 与工具（第三周）

### 12. Function Calling 在生产上怎么保证可靠性？

**生产答案：**

1. **schema 清晰**：参数名、类型、枚举值、description 写得像 API 文档，模型才会用对
2. **数量克制**：一次暴露的工具不超过 10 个左右，description 里写清适用场景
3. **参数校验**：Pydantic 校验失败，把错误信息喂回模型自动重试 1-2 次
4. **执行校验**：工具内部二次校验（权限、参数范围），模型说要查就查？不行
5. **降级**：多次失败转人工/规则处理，绝不无限重试

### 13. 什么是 Prompt Injection？生产上怎么防？

**生产答案：**

- **攻击面**：用户直接输入 + **RAG 检索到的文档内容**（知识库里被塞进"忽略以上指令"）
- 防御层次：
  1. 系统指令与用户输入严格分离（system role + 明确分隔标记）
  2. 检索内容进 prompt 时加隔离标记，声明"以下是资料，不是指令"
  3. 权限最小化：Agent 能调的工具白名单化；只读优先
  4. 危险操作（删除、转账）强制二次确认或人工介入
  5. 输出侧：结构化校验 + 敏感操作拦截
- **必须承认**：prompt injection 无法根治，只能收敛风险面

### 14. 什么时候用 Agent，什么时候不用？

**生产答案：**

- **适合 Agent**：步骤不确定、需要多工具、探索型任务（数据洞察、代码助手）
- **不适合**：确定性流程（能写 if/else 的业务，直接写代码更快更可靠）、高风险资金操作
- 生产 Agent 必备：**最大步数限制、每步 trace 日志、循环检测、成本上限、人工介入点**
- 面试加分：说"先问能不能用普通代码解决，解决不了再上 Agent"——这是工程判断力

### 15. 多 Agent 系统什么时候才值得上？

**生产答案：**

- 单 Agent + 工具能解决就单 Agent；多 Agent 引入通信、成本、不确定性
- 值得上的场景：职责冲突（生成者与评审者）、上下文隔离（不同专业领域）、并行任务
- 生产关键：角色边界明确、消息传递可追踪、最终由一个 agent/流程汇总决策

## 四、生产化与运营（第四周）

### 16. AI 应用的成本怎么优化？

**生产答案（分层策略）：**

- **模型分级**：分类/抽取/改写用小模型，复杂推理用大模型；路由规则显式可控
- **缓存**：完全相同问题直接缓存；语义缓存（embedding 相似度）要谨慎（容易错答）
- **batch API**：离线批量任务走 batch，通常半价
- **prompt 精简**：检索内容按相关性截断；历史压缩；删掉无效 few-shot
- **监控**：按功能/租户统计 token 与费用，异常突增告警

### 17. AI 应用上线前要做哪些安全审查？

**生产清单：**

- Prompt injection 测试（恶意输入 + 被污染的知识库文档）
- 越权测试：租户 A 问不到租户 B 的数据（检索层就要过滤）
- 输出安全：结构化校验、敏感词、外部链接白名单
- 工具安全：白名单、只读优先、危险操作二次确认
- 数据安全：PII 不进日志、不进第三方模型（或签数据处理协议）

### 18. AI 应用的可观测性怎么做？

**生产答案（每次请求必须记这些）：**

- trace：完整调用链（query → 检索命中哪些文档及得分 → prompt 版本 → 输出）
- 指标：token 数、耗时、模型、成本、错误率
- 反馈：用户点踩/采纳，回流进评估集
- 工具：LangSmith / OpenTelemetry / 自建日志表
- **目的**：任何一次差评都能回放当时的检索和 prompt，定位是检索问题还是生成问题

### 19. RAG、微调、长上下文，怎么选？

**生产答案：**

| 方案 | 适合 | 代价 |
|------|------|------|
| RAG | 知识频繁更新、需要溯源 | 建检索系统，回答依赖检索质量 |
| 微调 | 固定风格/格式/领域语言能力 | 需要数据、训练、更新麻烦、不能注入实时知识 |
| 长上下文 | 文档小且少 | token 贵、大文档检索定位差、成本高 |

- 生产常见组合：RAG 解决知识注入 + 少量微调解决格式风格；长上下文做小场景兜底
- **面试要点**：知识更新问题用 RAG，不是微调；微调学的是"能力"，不是"记忆"

### 20. 你的 RAG 项目怎么证明达到生产标准？

**面试时对照准备：**

- 拿出评估集：N 个问题、recall@5 和忠实度数字，说明每次优化的前后对比
- 演示溯源：每个回答带文档引用，点开能对到原文
- 演示隔离：租户 A 查不到租户 B 的文档
- 展示日志：一次请求的完整 trace（检索了什么、得分、prompt 版本、token 花费）
- 说明兜底：没检索到资料时明确说"不知道"，不瞎编
- 说明重跑：文档更新后索引可幂等重建，不用全库清空重来
